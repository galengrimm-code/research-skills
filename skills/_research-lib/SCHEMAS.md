# Shared metadata schemas (v3.0.3+)

This doc defines the YAML schemas that **all three research skills** (`/research`, `/deep-research`, `/content-research`) write so a future `/content-update` skill can perform delta-based re-pulls without re-fetching everything.

Two file types:

1. **`{archive}/recipe.yaml`** — per-archive metadata describing what was captured and how. Auto-generated on every skill run. Treat as machine-only; humans should read `INDEX.md` instead.
2. **`topics/{TopicArea}/MANIFEST.yaml`** — topic-area-level state store listing all archives + per-source checkpoints. Auto-updated on every skill run. Single source of truth for "what archives exist and when were they last touched."

Both use **schema_version: 1**. When the schema changes incompatibly, bump the version and document the migration path.

---

### Required fields (every source entry)

- `source_key` — deterministic stable identifier per the derivation rule below. Required so manifest merges don't churn keys between runs.
- `type` — one of: `website`, `youtube_channel`, `podcast`, `press_search`, `social_search`, `academic_openalex`, `github`
- `discovery_method` — how URLs/IDs were found
- `api_used` — which provider was hit
- `captured_count` — how many items landed in the archive
- `last_run_at_utc` — when this source was last touched (ISO-8601 UTC)
- `resumable` — can `/content-update` safely re-run this source? (false for one-shot extracts like a single PDF)

### Optional but valuable

- `last_seen_*` fields — anchor for delta detection in the next run
- `*_file` fields — path to captured IDs/URLs file (one per line) for efficient set-diff
- `interrupted_by` — null if clean, otherwise short reason string

### Identity rule

`canonical_entity_id` is **stable forever**. If "Dr. Henry Cloud" later goes by "Dr. H. Cloud" or moves domains, the `target.name` and `slug` can change but `canonical_entity_id` MUST stay `henry-cloud`. This is how the update skill matches archives across time.

### Identity resolution procedure (every run, including re-runs)

To prevent accidental canonical_entity_id changes, follow this order on EVERY skill invocation:

1. **Does the target archive folder already exist on disk?** Check `topics/{TopicArea}/{slug}-research-YYYY-MM-DD/` (or equivalent for /research and /deep-research). If multiple matches (different dates), prefer the most recent.
2. **If yes, read its `recipe.yaml`** and pull `target.canonical_entity_id` from there. REUSE this value verbatim. Do NOT derive a new one from the current run's slug.
3. **If no, check the topic-area MANIFEST.yaml** for an entry with a matching `path` or `slug`. If found, reuse its `canonical_entity_id`.
4. **If still no match, this is a first creation.** Set `canonical_entity_id` = `slug` (the freshly-derived slug from the current invocation).
5. **Optionally — if the user explicitly renames the target between runs** (e.g., they invoke /content-research with a new spelling for an entity that already has an archive), add the old name/slug to `recipe.yaml`'s `aliases[]` array as `{old_slug: "...", old_name: "...", changed_at_utc: "..."}` but DO NOT change `canonical_entity_id`.

Never compute `canonical_entity_id` from the current run's data when an existing archive is being updated. The identity is set on first creation and inherited forever.

### Per-skill schema extensions

The base schema covers all three skills. Skill-specific extensions:

- **`/deep-research`** may add these top-level fields to `recipe.yaml`:
  - `exposure: confirmed | likely | none | null` — to the user's stack
  - `cves: [CVE-YYYY-NNNNN, ...]` — list of CVE IDs analyzed
- **`/research`** may add:
  - `mode: how-to | comparison | explainer | landscape` — the research mode classified in Step 1
- **`/content-research`** has no additional top-level fields beyond the base schema.

**Skills MUST NOT add other top-level fields without updating this SCHEMAS.md document and bumping `schema_version`.** Parser breakage on unexpected fields is exactly the kind of drift this whole scaffolding is designed to prevent.

The only exception is the `backfilled: true` flag added by the one-time `_BACKFILL.py` script (documented in the Backfill section below). It's a permitted top-level meta-field and does NOT require a schema_version bump — it's part of the v3.0.3 contract.

## File 2: `topics/{TopicArea}/MANIFEST.yaml`

Topic-area state store. Lists every archive in this topic-area with summary state. Auto-updated by the skill on every run.

```yaml
---
schema_version: 1
topic_area: Leadership
last_updated_at_utc: 2026-05-21T07:15:00Z

archives:
  - slug: craig-groeschel
    canonical_entity_id: craig-groeschel
    path: craig-groeschel-research-2026-05-18
    created_at_utc: 2026-05-18T16:26:00Z
    last_updated_at_utc: 2026-05-19T14:05:00Z
    skill_version_at_creation: "3.0.1"
    skill_version_at_last_update: "3.0.1"
    has_recipe_yaml: false                # pre-3.0.3 archives don't have one until backfilled
    sources_summary:
      podcast_listen-notes_craig-groeschel-id: { captured: 193, pending: 0, last_run_at_utc: "2026-05-19T14:05:00Z" }

  - slug: henry-cloud
    canonical_entity_id: henry-cloud
    path: henry-cloud-research-2026-05-21
    created_at_utc: 2026-05-21T06:58:00Z
    last_updated_at_utc: 2026-05-21T07:15:00Z
    skill_version_at_creation: "3.0.3"
    skill_version_at_last_update: "3.0.3"
    has_recipe_yaml: true
    sources_summary:
      website_drcloud.com: { captured: 9, pending: 0, last_run_at_utc: "2026-05-21T07:05:00Z" }
      website_boundaries.me: { captured: 52, pending: 1414, last_run_at_utc: "2026-05-21T07:05:00Z" }
      youtube_DrHenryCloud: { captured: 367, pending: 323, last_run_at_utc: "2026-05-21T07:12:00Z" }
      podcast_listen-notes_35bb4ffca12b478abd32611a4504ee80: { captured: 10, pending: 90, last_run_at_utc: "2026-05-21T07:00:00Z" }
```

### Required fields per archive entry

- `slug`, `canonical_entity_id`, `path` — identity
- `created_at_utc`, `last_updated_at_utc` — timeline
- `skill_version_at_creation`, `skill_version_at_last_update` — for compat detection
- `has_recipe_yaml` — true once 3.0.3 has touched the archive
- `sources_summary` — compact per-source state (the full data lives in the archive's `recipe.yaml`)

### MANIFEST merge key — CRITICAL

When a skill run touches an archive that already has a manifest entry, the merge MUST use this key precedence (never `slug` alone — slug can change on rename):

1. **First — match by `canonical_entity_id`.** If found, update that entry. This is the load-bearing identity.
2. **Fallback — match by `path`.** If found and `canonical_entity_id` field is missing/empty (legacy entries), update that entry AND populate its `canonical_entity_id` from the archive's `recipe.yaml`.
3. **Otherwise — append new entry.** First-creation case.

NEVER match by `slug` alone. If the user renames the target between runs (e.g., "Henry Cloud" → "Dr. H. Cloud"), the slug may change but `canonical_entity_id` stays put. Matching on slug would silently fork identity.

### `source_key` derivation rule (sources_summary and recipe.yaml sources[] entries)

Use deterministic keys so merges don't churn between runs:

- `website_{registrable-domain}` — e.g., `website_drcloud.com`, `website_boundaries.me`
- `youtube_{channel-handle-without-@}` — preserve original casing of the handle as it appears on YouTube (e.g., `youtube_DrHenryCloud`). Don't lowercase — handles are case-sensitive on YouTube and lowercasing creates collisions.
- `podcast_{provider}_{provider-id}` — e.g., `podcast_listen-notes_35bb4ffca12b478abd32611a4504ee80`
- `press_search` (single key, queries inside the entry)
- `social_search` (single key, queries inside the entry)
- `academic_openalex_{author-id}` — e.g., `academic_openalex_A5012345678`
- `github_{user-or-org}` — e.g., `github_galengrimm-code`

Hyphens preserved, periods kept in domains. Preserve original casing of platform handles (YouTube, GitHub) since those are case-sensitive. Lowercase only generic-string segments (e.g., the `website`/`youtube`/`podcast` type prefix). The key is stable across runs of the same skill on the same target.

### Ungrouped archives

For archives without a topic-area:
- In `recipe.yaml`, set `target.topic_area: null` (YAML null, not the string `"ungrouped"` or empty string).
- Write the manifest to `topics/MANIFEST.yaml` (at `topics/` root, not under any subfolder).
- The manifest's `topic_area` field is also `null`.

### Stable item IDs — required for all resumable sources

Every source entry with `resumable: true` MUST write a captured-IDs file in `_raw/` containing **stable item identifiers**, one per line. Counts alone are not enough — v3.1 tombstone detection needs to identify which specific items disappeared between runs.

- YouTube: 11-char video IDs
- Podcast (Listen Notes): episode IDs (hex hashes from API)
- Website: full URLs (the URL is the identity)
- Press / social: full URLs (with normalization — strip tracking params like `?utm_*`)
- Academic: DOIs (preferred) or OpenAlex work IDs
- GitHub: repo full_name (`owner/repo`)

If a source can't produce stable IDs (rare — only true for one-shot extractions), set `resumable: false` and document why in `interrupted_by` or a comment.

### How the update skill uses this

```python
# Pseudo-code for /content-update --topic-area=Leadership
manifest = read_yaml("topics/Leadership/MANIFEST.yaml")
for archive in manifest["archives"]:
    if not archive["has_recipe_yaml"]:
        log(f"Skipping {archive['slug']} — no recipe.yaml. Run backfill first.")
        continue
    recipe = read_yaml(f"topics/Leadership/{archive['path']}/recipe.yaml")
    for source in recipe["sources"]:
        if not source["resumable"]: continue
        deltas = enumerate_source_and_diff(source)
        if deltas:
            fetch_and_append(deltas, archive['path'])
            update_recipe(source, new_state)
    update_manifest(archive, new_state)
```

## Backfill — adding metadata to pre-3.0.3 archives

A one-time script reads every existing archive's INDEX.md and infers the source list from folder structure (`01_website/` → website, `02_youtube/transcripts/` → youtube, etc.), then writes a `recipe.yaml` + entry in the per-topic-area `MANIFEST.yaml`.

**The script MUST scan all five archive folder patterns:**

1. `topics/{TopicArea}/{slug}-research-YYYY-MM-DD/` — content-research output (new convention, post 2026-05)
2. `topics/{TopicArea}/{slug}-research/` — content-research output (legacy pre-2026-05, no date)
3. `topics/{TopicArea}/{slug}-YYYY-MM-DD/` — research output (topic syntheses)
4. `topics/{TopicArea}/{slug}-security-YYYY-MM-DD/` — deep-research output
5. `topics/{slug}-YYYY-MM-DD/` — ungrouped topic syntheses (any of the above without a topic-area)

For each archive, determine `skill_name` by:
- INDEX.md frontmatter `type` field (preferred — content-research / research / deep-research)
- Fallback: folder-name pattern (has `-research-` → content-research, has `-security-` → deep-research, otherwise research)

Backfilled `recipe.yaml` will have less detail than freshly-generated ones (no `last_seen_*` anchors, no captured-IDs files) but enough to identify the archive and its sources so future updates can re-enumerate from scratch. Backfilled entries are flagged with `backfilled: true` at the top level of recipe.yaml.

See `~/Documents/AI/Content extraction/_BACKFILL.py` (created at v3.0.3 install time).
